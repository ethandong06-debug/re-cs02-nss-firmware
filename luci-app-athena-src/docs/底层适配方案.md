# AthenaWrt 底层适配方案 v2

> 面向京东云雅典娜 AX6600（RE-CS-02 / IPQ6010）的底层深度适配
> 原则：**吃透每一个硬件子系统，如实区分「开源能做到」与「受限于闭源」**
> 约束：**不做任何分区重划 / GPT 大分区等改动分区表的操作**（用户明确要求）

---

## 一、目标

1. 让 IPQ6010 的网络转发、无线、存储、USB、点阵屏、温控能力发挥到极限。
2. 对无法在官方主线启用、但社区分支已实现的能力（NSS）如实说明并采用。
3. 为前端 `luci-app-athena` 提供稳定、准确的硬件数据源。

---

## 三、各子系统适配方案

### 3.1 CPU 与 NPU
- **满频解锁**：确认 cpufreq 跑满 1.8GHz（而非默认限频），governor `ondemand`，
  负载高时稳定冲顶；验证四核是否全部上 1.8GHz。
- **IRQ 亲和性**：网卡/无线中断绑定到不同核，避免单核瓶颈。
- **NPU（1.5GHz 网络核）**：即 NSS 核，见 3.2。
- **编译优化**：目标 CPU 用 `cortex-a53` + 硬浮点（已配置）。

### 3.2 网络转发（NSS 硬件加速，社区分支启用）
**结论已更正**：NSS 在官方主线不启用，但**社区分支已成熟实现**，且覆盖 IPQ60xx/雅典娜。

- **采用方案**：切换到社区 NSS 分支（`qosmio/openwrt-ipq` 或 `dvb001/openwrt-6.x`，
  均基于 ImmortalWrt 体系），引入 `qosmio/nss-packages` feed。
- **关键包**：`kmod-qca-nss-drv` + `nss-firmware-ipq60xx`（从原厂固件提取的 blob）
  + `kmod-qca-nss-ecm` + `kmod-qca-nss-crypto` + `kmod-qca-nss-drv-pppoe`。
- **收益**：NAT/转发/PPPoE/VLAN/多播 硬件卸载，实测路由+VPN 吞吐翻 3-5 倍。
- **叠加**：RPS/RFS 多核包处理（Packet Steering），与 NSS 协同压榨 4 核。
- **组网模式适配**：NSS 对「拨号 / AP / 单臂 / 旁路由」四种组网方式的处理策略不同，
  **单臂路由可保留 NSS（走 VLAN offload），旁路由应关闭 offload**，详见 3.12。

### 3.3 2.5G 口满速
- 确认 QCA8081 PHY 驱动（`qca808x`）正确协商 2500base-x。
- 开启 flow control（pause 帧）、关闭 EEE（2.5G 下有兼容性问题）。
- 提供协商速率强制选项（2500 full / 1000 / 100），供前端展示与控制。

### 3.4 无线三频
- 三频：2.4G（板载 2×2，574M）+ 5.8G（板载 2×2，1201M）+ 5.2G（QCN9074 4×4，4804M）。
- 校准数据 `ipq-wifi-jdcloud_re-cs-02` 已随固件打包。
- **160MHz + DFS 解锁**：QCN9074 支持 160MHz 频宽和 DFS 雷达信道，解锁更多高速信道。
- **无线内存水位线调优**：防 ath11k 高负载长期运行内存上涨导致断流。
- **游戏专属频段（SmartGaming）**：5.2G 4804M 做游戏加速 / 低延迟 QoS。
- **三频 Mesh + 独立回程**：5.2G 可作专用回程频段。
- 明确标注频段来源芯片，供前端三频卡片区分。

### 3.5 存储 eMMC（挂载，不重分区）
- **现状**：`.config` 未启用 `kmod-mmc`，128GB eMMC 无法识别。
- **补齐**：启用 `kmod-mmc` + 高通 SDHC 驱动（`mmc-msm`/`sdhci-msm`），
  让 `&sdhc` 节点（8-bit HS200）工作。
- **挂载方案（不重新分区）**：
  1. 直接挂载 eMMC 现有分区（或整盘）为 `ext4` 数据盘；
  2. 可作 overlay 扩展（解决 128M NAND 根空间小）或 Samba 共享 / Docker 数据盘。
  - **明确不碰**：boot/rootfs 分区表、GPT 大分区重划。
- 挂载参数用 `noatime` 减少写放大、延长 eMMC 寿命。

### 3.6 USB 3.0
- 启用 UAS + `usb-storage-uas`（已配置），外接至 4TB。
- 5V 电源由 gpio22 控制（`usb_vbus` regulator）。
- **干扰抑制**：USB3 会干扰 2.4G，提供 USB 工作模式切换规避。

### 3.7 硬件加密引擎（qcrypto/CE）
- IPQ6010 有独立硬件 AES 引擎，启用 `qce`（Qualcomm Crypto Engine）驱动。
- 加速 **IPsec / WireGuard / OpenVPN**，跑 VPN 时显著降 CPU 占用。
- 与 NSS crypto 互补。

### 3.8 点阵屏（标志性硬件，重点定制）
- **现状**：刷第三方固件后点阵屏变"砖头"，需接入社区驱动（如 `luci-app-athena-led`）。
- **定制显示内容**：时间 / 实时流量 / 在线设备数 / CPU 温度 / WiFi 状态。
- 前端提供「点阵屏显示内容」配置页。

### 3.9 温控与功耗
- 启用 `thermal` + `hwmon`，暴露多热区温度。
- 被动散热（无风扇），无需风扇 PWM；前端画温度历史曲线。

### 3.10 内存（1GB DDR4）
- 启用 `zram` 压缩交换（1GB 足够跑 Docker 等重应用）。
- 网络缓冲区、conntrack 连接数上限按 1GB 合理调大。

### 3.11 LED 与按键
- 三色 LED 通过 `/sys/class/leds/*` 暴露，自定义各状态颜色。
- reset/screen/wps 三键通过 `gpio-button-hotplug` 转 key event，前端绑定自定义动作。

### 3.12 组网方式与 NSS 适配（拨号 / AP / 单臂 / 旁路由）

> 重要更正：早期结论「单臂路由必须关 NSS」**不准确**。查证 NSS Support Matrix
> （qosmio/xhikarishii `openwrt-ipq`）与 ppe-nss 路线后确认：**VLAN offload 是支持的**，
> 单臂路由（本质是 VLAN）可以保留 NSS。真正需要「关 offload」的是**旁路由**，
> 且那是「正确做法」而非「妥协」——因为旁路由的流量必须经过 CPU 上的代理/去广告软件。

#### 3.12.1 四种组网方式的 NSS 定位

| 组网方式 | 流量性质 | NSS/offload 策略 |
|----------|----------|------------------|
| 拨号上网（PPPoE/DHCP 主路由） | 纯 NAT 转发 | ✅ 开 NSS（PPPoE 加 `nss-drv-pppoe`） |
| AP 桥接 | 无 NAT，纯桥接 | 不涉及（桥接不占 CPU，无需 offload） |
| **单臂路由**（主 NAT + VLAN） | 纯转发 + VLAN tag | ✅ 开 NSS（走 DSA VLAN offload，见 3.12.2） |
| **旁路由**（代理/去广告） | 流量必须过 CPU 软件 | ❌ 关 offload（正确做法，避免绕过代理） |

#### 3.12.2 单臂路由 + NSS 完整组网方案

**拓扑**：雅典娜一个物理口（**建议用 2.5G 口**，单臂所有流量挤一条链路，带宽需求最大）
上接网管交换机 / 光猫，通过 802.1Q VLAN 区分 WAN 与 LAN。

```
              ┌─────────────────────┐
 光猫/交换机 ──│  2.5G 口 (trunk)    │
  (VLAN 打 tag)│   VLAN 10 = WAN     │──→ 雅典娜 CPU + NSS
              │   VLAN 20 = LAN     │
              └─────────────────────┘
```

**VLAN 划分设计（逻辑）**：

| 用途 | VLAN ID | 方向 |
|------|---------|------|
| 上行（WAN，接光猫/上级） | 10 | tagged trunk |
| 下行（LAN，接内网设备） | 20 | tagged trunk |

**关键配置原则（决定 NSS 能否 offload）**：

1. **必须用 DSA 的 bridge VLAN filtering**，在 `br-lan` 交换机层打 VLAN tag；
   **不要**用 Linux 软件 VLAN 子接口（`eth0.10` / `eth0.20`）。
   NSS 对 DSA 交换机层 VLAN 的卸载支持最好，对 Linux 软件子接口支持差。
2. 关闭软件 `flow offload`（`nft-offload`），避免与 NSS 冗余卸载冲突。
3. 确认 `nss-ecm` 能正确识别带 tag 的流（配置完成后 `cat /proc/sys/dev/nss/*/stats` 验证）。

**必须实测的项（hairpin 风险）**：

- 单臂流量**同一口进出两次**（hairpin），是 NSS offload 最容易翻车的场景；
  矩阵里的 VLAN ✅ 只代表「功能存在」，不代表「单臂 hairpin 一定稳」。
- 实测清单：① 挂载测速（单臂上下行对跑）② 长时间大流量压测 ③ 观察是否断流/延迟异常。
- **兜底**：若 hairpin 实测不稳，退回到软件 `flow offload`（IPQ6010 软转发单臂也能到千兆）。

**真机确认项**：DSA 端口命名（`lan1`~`lan5` 对应哪个物理口）、trunk 口的 tag 配置，
需在切换分支后按实际 DTS/网络配置核对，本文给出的是原则性方案。

## 四、明确排除项（用户要求）

| 排除 | 原因 |
|------|------|
| NAND GPT 大分区重划 | 改动分区表，风险高 |
| 双分区 / 不死 U-Boot 重刷 | 改动引导分区 |
| 任何 `parted`/`fdisk` 重分区操作 | 数据风险 |

## 六、诚实的技术边界

| 能力 | 能否做到 | 说明 |
|------|----------|------|
| 2.5G 口满速 | ✅ 能 | 开源驱动成熟 |
| 三频无线满配 + 160MHz | ✅ 能 | ath11k 成熟 |
| eMMC 128G 挂载 | ✅ 能 | 补 mmc 模块即可 |
| NSS 硬件加速 | ✅ 能（社区分支） | qosmio 等已成熟，需换分支 |
| 单臂路由 + NSS | ⚠️ 能（需实测） | VLAN offload 支持，但 hairpin 需真机验证 |
| 旁路由 + NSS | ❌ 不应开 | offload 会绕过代理，关掉才是正确用法 |
| 点阵屏定制 | ✅ 能（社区驱动） | 有现成驱动 |
| 硬件加密引擎 | ✅ 能 | qce 驱动 |
| 官方边缘计算/积分 | ❌ 不能 | 京东云闭源业务 |
| 分区重划/大分区 | ❌ 不做 | 用户明确排除 |

## 八、与前端方案的衔接

底层提供数据、前端呈现数据。M4 的 ubus 聚合脚本 + 点阵屏/LED 状态，
正是前端仪表盘/端口/三频/eMMC/点阵屏/温度各页面的数据源。
两部分合并，即构成完整的「AthenaWrt 定制固件」。

# AthenaWrt V1.0 前端接入基线（菜单冻结版）

> 状态：接入基线已确认；尚未替换设备端前端，也未生成或安装新 APK。  
> 目标分支：`athenawrt/v1-html-integration`  
> 基础包：`luci-app-athena 1.2.60-r5`

## 1. 用户明确确认的边界

- **V1.0 菜单必须原样保留。** 不重命名、不增删、不合并、不拆分、不调序、不改变分组和页面归属。
- 本轮仅处理页面视觉、布局、交互、数据接入、后端调用、错误反馈、权限与安全校验。
- 使用独立 LuCI APK；不重刷固件，不重编译整套固件。
- 不修改 PPPoE、VLAN 2044、IPv6、Firewall、OpenClash、NSS/ECM 的现网配置。
- 未经明确授权，不执行会改变 WAN/LAN/桥接/VLAN/组网模式的操作。
- 所有未接入真实后端的控件必须标记为不可用/待接入，不能用模拟成功提示冒充真实执行。

## 2. 冻结的 V1.0 菜单（来自用户上传 HTML）

以下内容从 V1.0 HTML 的 `window.groups` 原始定义提取。它是本轮唯一菜单基准：

| 分组顺序 | 页面顺序 |
|---|---|
| 总览 | 首页仪表盘 |
| 无线 | 三频 WiFi、访客网络、WiFi 定时 |
| 网络 | 工作模式与 WAN、基础网络服务、网络诊断 |
| 终端 | 终端列表、家长控制 |
| 存储 | 存储与磁盘管理、NAS 文件共享 |
| 系统 | 系统维护与备份、雅典娜点阵屏、系统日志、软件包管理 |

合计：**6 个分组、15 个页面**。菜单的分组名、页面名、顺序和归属全部冻结。

注意：现有设备端 APK 的 LuCI 外层菜单（AthenaWrt / 高级模式）与应用内部 V1.0 菜单是两个层级。本轮不改动现有 LuCI 外层菜单 JSON，也不把其他工程菜单结构强加给 V1.0。

## 3. 接入架构

- 前端：以用户上传的 V1.0 HTML 为视觉和交互基准。
- 认证：沿用 LuCI/rpcd 的真实登录会话；禁止前端本地状态绕过登录。
- API：复用现有 `athenaRPC` 适配层和已存在的 `/usr/libexec/athena-*.sh` 脚本。
- 权限：维持 rpcd ACL 的脚本逐项授权，不授予任意 shell 执行能力。
- 打包：继续使用 `luci-app-athena` APK 和 GitHub Actions 签名流程。
- 原生 LuCI：保留现有入口作为维护回退路径。

## 4. V1.0 页面到现有后端能力的初步映射

| V1.0 页面 | 现有后端候选 | 接入原则 |
|---|---|---|
| 首页仪表盘 | `athena-status.sh`、`athena-resources.sh`、`athena-accel.sh` | 实时采集；不显示随机生成的设备速率；模块存在不等于实际硬件卸载命中 |
| 三频 WiFi | `athena-wireless.sh` | 先核对本机真实无线 section、phy、频段映射，再允许写入 |
| 访客网络 | `athena-wireless.sh guest` | 先验证隔离接口、防火墙和 DHCP 状态；不假定 br-guest 已存在 |
| WiFi 定时 | 现有无线/计划任务后端需核对 | 只管理 Athena 自己的任务，不覆盖 root crontab 其他条目 |
| 工作模式与 WAN | `athena-mode.sh`、状态脚本 | 对当前设备默认只读；不调用会重建网络配置的 router/single/bypass/AP 切换命令 |
| 基础网络服务 | 当前脚本能力需逐项核对 | PPPoE、VLAN、IPv6、DNS、DHCP、防火墙默认只读；不做批量重写 |
| 网络诊断 | `athena-diag.sh` | 允许 ping/DNS/状态检查；禁止隐式改路由或重启网络 |
| 终端列表 | `athena-client.sh`、状态脚本 | 展示来源和在线状态；踢除/拉黑必须有真实实现、二次确认和结果校验 |
| 家长控制 | `athena-parent.sh` | 验证规则持久化、定时器和撤销行为后再启用写操作 |
| 存储与磁盘管理 | `athena-disk.sh` | 仅允许真实 USB 分区；格式化前拒绝已挂载、swap、系统盘和整盘设备 |
| NAS 文件共享 | `athena-nas.sh` | 仅共享已验证挂载到 `/mnt/usb` 的目录；随机密码、LAN 访问范围、权限边界必须验证 |
| 系统维护与备份 | `athena-backup.sh`、`athena-reboot.sh`、`athena-upgrade.sh`、`athena-reset.sh` | 备份可先接入；恢复、重启、升级、重置必须分开确认并检查返回结果 |
| 雅典娜点阵屏 | `athena-matrix.sh`、`athena-led.sh` | 只写专属配置；验证驱动和配置段存在 |
| 系统日志 | `athena-log.sh` | 读取/导出/清理分别授权和确认 |
| 软件包管理 | `athena-packages.sh` | 保留关键包保护；禁止卸载或升级 OpenClash、NSS/ECM、内核和网络基础组件 |

## 5. 已核对的工程事实

- 当前 APK Makefile 版本为 `1.2.60-r5`。
- Makefile 安装 38 个 libexec 文件（包括 shell、ucode、legacy 和 helper）。
- 当前前端中存在 26 个不同的 `athenaRPC.exec()` 脚本目标。
- 当前 rpcd ACL 对应授权 26 个 Athena 脚本入口；后续每次新增脚本都必须同步检查 Makefile 与 ACL。
- `athena-accel.sh` 明确报告的是模块存在情况，不能单独证明 NSS/ECM 数据面正在命中。
- `athena-disk.sh` 已有 USB 分区、挂载状态、swap 和系统盘拒绝检查；仍需针对本机块设备拓扑做验证。
- `athena-nas.sh` 已包含 USB 挂载检查、固定共享根目录和随机密码相关逻辑；仍需核实实际 LAN 绑定和文件系统权限行为。
- `athena-mode.sh` 包含网络配置创建/删除和模式切换逻辑，影响面远大于普通 UI 设置。当前设备的该类写操作必须在前端和后端双重阻断，除非用户另行明确授权。

## 6. 实施顺序

1. 以原始 V1.0 菜单定义建立自动校验基准；任何菜单差异都视为失败。
2. 将 V1.0 页面组件迁入现有 SPA，先完成纯前端渲染与移动端布局；不改菜单。
3. 接入真实登录会话，删除预览模式自动登录、单臂入口和伪成功逻辑。
4. 建立统一 API 结果规范：`ok`、`data`、`error`、`source`、`updated_at`；超时、ACL 拒绝和脚本非零退出必须显示失败。
5. 逐页接入只读数据，再逐项开放低风险写操作。
6. 对网络、磁盘、NAS、包管理、恢复/升级等高风险功能做双重校验和确认流程。
7. 执行 HTML/JS 语法检查、菜单一致性检查、RPC→ACL→Makefile 三方一致性检查和 APK 构建验签。
8. 通过静态检查后再安排设备端验收；不在当前在线路由器上做网络模式切换、格式化、恢复或升级测试。

# AthenaWrt 功能架构与优化执行原则

> 实时进度、提交、构建和设备验收只维护在 `ATHENAWRT-PROJECT-STATUS.md`。本文件只保留长期决策原则。
> 更新日期：2026-11-03

## 1. 目标

在不破坏现有网络、硬件加速和用户功能的前提下，修复 Athena 的安全与状态真实性问题，优化 Athena 自有页面，并维持独立 APK 交付。

## 2. 必须保持的边界

- 不改变 PPPoE、VLAN 2044、IPv6 PD/SLAAC、防火墙/NAT、OpenClash、NSS/ECM 驱动及硬件加速现网状态。
- 不在在线设备试错固件刷写、恢复出厂、网络模式切换、重启网络或磁盘格式化。
- **任何原生 LuCI 页面、菜单、ACL、软件包管理器及后端均不属于 Athena 修改范围。**
- 不刷写整机固件；继续使用 GitHub Actions 构建独立 APK并通过签名、哈希验证。

## 3. 功能决策原则

- 保留：硬件状态仪表盘、三频快捷操作、单臂/VLAN 专用能力、设备识别、LED/点阵屏和必要存储能力。
- 原生替代：通用系统管理能力可以从 Athena 跳转原生 LuCI，但不得为了实现 Athena 安全限制而修改原生组件。
- 重做：仅对有证据的安全、事务、状态真实性或错误处理缺陷进行修改。
- 移除：只有确认无调用者、无兼容依赖后才移除。
- 不增加 NSS/ECM 前端开关；不把 DNS/OAF 推测为 DPI；不把静态拓扑或动画冒充实时数据。

## 4. 安全整改重点

1. Athena ACL 只保留实际调用链所需权限。
2. 固件升级后端在 flash 阶段重新核验路径、目标机型、归档结构、哈希与 sysupgrade 平台验证。
3. 恢复出厂、服务启停和网络模式的危险分支必须由后端约束，不依赖前端隐藏按钮。
4. Athena 包管理对关键组件做直接保护及依赖事务预演；不修改原生 package-manager。
5. 备份恢复、USB 设备身份、nftables 规则所有权与多 UCI 事务仍按 P1 继续专项审计。

## 5. Athena 页面设计原则

- 标准 Liquid Glass；均衡密度、清晰层级、克制动效。
- 默认跟随系统明暗主题，允许用户手动浅色/深色覆盖，并持久化所选模式。
- 桌面/平板有效利用多列布局；手机保持单列、完整文字和可触控控件。
- 实时数值必须来自真实 RPC；无数据或读取失败时显示未知/读取中，不以示例数据伪装。
- 保留 Athena 既有功能分工，不为普通体验优化而重写整套 SPA 或修改原生 LuCI。
- 通过静态语法、调用链、mock/CI 和签名/哈希验证；危险设备操作不做真机试错。

## 6. 实施流程

用户要求相关工作一次完成时，将同一范围的 Athena 源码修改合并为完整批次；完成全部修改后再统一验证和构建。若用户没有要求拆分，不逐项请求操作确认。
